# MicroScan
A tool which I'm developing for my Thesis

## Authentication checks

The existing `GET /scan?target=...` API and Kiterunner discovery flow are retained. When an explicit `MICROSCAN_JWT_ENDPOINT_ALLOWLIST` is configured as a JSON array of `{ "method": "GET", "path": "/api/resource/1" }` entries, it remains the mandatory boundary and each matching endpoint is tested; automatic-selection limits do not truncate an explicit allowlist. Without a non-empty allowlist, the Scan page automatically selects candidates only for loopback targets (`localhost`, `127.0.0.0/8`, or `::1`); the backend enforces this restriction. Auto-selection uses only current Discovery records, prioritizes sensitive routes such as `/api/orders/check/` and `/api/admin/dashboard`, then protected-resource candidates returning HTTP 200 and 401/403. Discovery status is only a selection signal, not a finding. Login/registration and health/debug routes are excluded. By default at most five route groups are selected per scan; set `MICROSCAN_JWT_ENDPOINT_BUDGET` to an integer from 1 to 100 to adjust that cap. One discovered ID represents a group such as `/api/orders/1` and `/api/orders/2`; sibling IDs remain explicitly untested and no result is inferred for them. Trailing-slash variants remain separate routes. Only `GET` probes execute. Other methods and routes that do not meet selection rules are reported as `skipped`, not treated as safe. Exact duplicate Discovery records are collapsed by method and path. `MICROSCAN_PROTECTED_ENDPOINT` remains supported as a legacy, single-path `GET` allowlist entry.

For each selected `GET`, MicroScan records independent no-token and structurally valid JWT-with-invalid-signature cases. A configured login may supply a valid-token comparison; a request error on one case does not prevent later cases or endpoints from running. Valid JSON, error envelopes, generic messages, and empty collections are not treated as resource disclosure. A potential resource finding requires a bounded sanitized sample of record-shaped data (field names and value types only; response values and raw bodies are not retained). If an error/denial signal and resource-record sample coexist, the report preserves the conflict and explains that the sample must be verified. Structured resource data without credentials is `potential` unless explicit endpoint metadata establishes the authentication policy: `authentication_required=true` can support a `confirmed` finding only when the same response does not indicate denial, while `false` identifies a public resource for that case. Without policy metadata, generic 2xx messages or bodies without resource records are `inconclusive`. HTTP 401/403 and body/challenge signals are evidence of denial, but do not by themselves prove that resource data was absent when the body could not be assessed. Expired-token probing is not implemented and is recorded as `skipped`; it affects coverage only and does not replace results from other cases, and MicroScan does not infer signing keys or mint expired tokens. Endpoint selection is recalculated from the current Discovery result on each scan; selection or a mock test is not counted as an actual probe. The summary distinguishes discovered, selected, tested, partially tested, inconclusive, and untested endpoints from test-case outcomes and request attempts. Skipped and not-implemented counters are disjoint in the executive summary: not-implemented cases have raw `skipped` status but are excluded from the separate skipped count. Endpoint details and findings display the same sanitized test-case evidence.

The backend also produces a pentest conclusion and executive summary from the collected test-case evidence. Only `confirmed` and `potential` cases are emitted as vulnerability findings; `not_vulnerable_in_test` and coverage statuses remain test outcomes. Incomplete endpoint coverage, skipped/unimplemented cases, inconclusive results, and request errors prevent a clean negative conclusion. `No Vulnerabilities Detected in Tested Scope` is limited to a fully completed test scope and is not a claim that the system is secure. Discovery/scan failures return a `Scan Failed` report with no fabricated findings.

Login/token endpoints are identified only from discovered `POST` routes that resemble authentication or token endpoints. Discovery does not reveal a request schema, so MicroScan never guesses a login body, creates accounts, or submits credentials automatically. To enable optional authenticated coverage, provide the documented lab credentials or payload. MicroScan loads `.env` from the repository root using `python-dotenv`; values already set in the operating-system environment take precedence. The root `.env` is ignored by Git; use `.env.example` as a template:

- `MICROSHIELD_USERNAME` and `MICROSHIELD_PASSWORD`: build the lab's documented `username` / `password` JSON payload when both values are present.
- `MICROSCAN_LOGIN_ENDPOINT`: optional path or same-origin absolute URL; otherwise the first discovered login candidate is used.
- `MICROSCAN_LOGIN_PAYLOAD`: optional legacy JSON payload object, used instead of the username/password pair when present.
- `MICROSCAN_AUTH_CONFIG`: JSON object with a `payload` object, and optional `login_endpoint`, `content_type`, `method` (`POST` only), `token_field`, `auth_header`, and `auth_scheme`.
- `MICROSCAN_JWT_ENDPOINT_ALLOWLIST`: optional JSON array of explicit `{ "method": "GET", "path": "/api/resource/1" }` targets. Paths must be origin-relative and must not include query or fragment data. Only `GET` is probed; other configured methods are reported as skipped.
- `MICROSCAN_JWT_ENDPOINT_BUDGET`: optional automatic-selection cap (integer 1-100); defaults to five route groups. It does not limit explicit allowlists.
- `MICROSCAN_PROTECTED_ENDPOINT`: legacy optional path, treated as one explicitly allowlisted `GET` target. It is not a substitute for an API-wide allowlist.

The payload must match the lab's real contract. MicroScan extracts a token only from supported response fields or the configured `token_field`; it sends a valid-token probe only after login actually succeeds. The authorization scheme is taken from configuration, the login response, or an observed challenge. If none is present but the returned token has the standard three-part JWT shape, MicroScan makes a best-effort `Bearer` request and labels that scheme as inferred rather than observed. Other token formats require an explicit or observed scheme. Secrets and raw response values are not included in reports. `confirmed`, `potential`, `not_vulnerable_in_test`, `inconclusive`, and `skipped` describe only the evidence and coverage from this particular endpoint/test case.

Example allowlist:

```text
MICROSCAN_JWT_ENDPOINT_ALLOWLIST=[{"method":"GET","path":"/api/users/me"},{"method":"GET","path":"/api/orders/1"}]
```

Install backend dependencies from the repository root with `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`. Copy `.env.example` to `.env` and replace the placeholders with authorized lab credentials (or set the environment variables in your shell). Do not commit `.env` or put credentials in reports:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# Edit .env with the authorized lab values before starting the backend.
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

To run basic unauthenticated checks, leave the authentication variables unset. Start the frontend in a separate shell with `cd frontend` and `npm run dev`, then enter the authorized target origin on the Scan page. Unit tests use mocked HTTP responses; they do not establish the behavior or vulnerability status of a live lab.
