# MicroScan
A tool which I'm developing for my Thesis

## Authentication checks

The existing `GET /scan?target=...` API and Kiterunner discovery flow are retained. The Scan page defaults to **Standard Scan**, which preserves the five-group JWT selection budget, route-shape representative selection, and current prioritization. **Full Scan** tests every eligible concrete discovered JWT endpoint without that group budget; sibling IDs that Standard groups together are tested individually in Full mode, so it may take longer and generate more requests. Full mode retains GET-only checks, loopback restriction for automatic JWT selection, authorized-scope enforcement, authentication-route exclusions, dynamic-template exclusions, request timeouts, and the active BOLA request cap. The streamed Scan page offers cancellation; the current endpoint's bounded check sequence may finish within existing request timeouts, while the UI marks running stages cancelled and does not present a partial scan as completed. Full mode removes only the JWT endpoint-group selection budget, not other safety limits.

When an explicit `MICROSCAN_JWT_ENDPOINT_ALLOWLIST` is configured as a JSON array of `{ "method": "GET", "path": "/api/resource/1" }` entries, it remains the mandatory boundary and each matching endpoint is tested; automatic-selection limits do not truncate an explicit allowlist. Without a non-empty allowlist, the Scan page automatically selects candidates only for loopback targets (`localhost`, `127.0.0.0/8`, or `::1`); the backend enforces this restriction. Auto-selection uses only current Discovery records, prioritizes sensitive routes such as `/api/orders/check/` and `/api/admin/dashboard`, then protected-resource candidates returning HTTP 200 and 401/403. Discovery status is only a selection signal, not a finding. Login/registration and health/debug routes are excluded. In Standard mode, one discovered ID represents a group such as `/api/orders/1` and `/api/orders/2`; sibling IDs remain explicitly untested and no result is inferred for them. Full mode probes each eligible concrete ID separately. Trailing-slash variants remain separate routes. Only `GET` probes execute. Other methods and routes that do not meet selection rules are reported as `skipped`, not treated as safe. Exact duplicate Discovery records are collapsed by method and path. `MICROSCAN_PROTECTED_ENDPOINT` remains supported as a legacy, single-path `GET` allowlist entry.

JWT selection now consumes the merged, scope-checked discovery inventory and uses each record's resolved URL for the request origin while retaining its original URL and evidence. A resolved API GET returning 401/403 remains eligible for an independent JWT probe even when File Discovery labels it `blocked`; that discovery response is not itself a vulnerability finding. A 405 route is excluded for its observed method without inventing another method. Unknown methods, unresolved templates, origin roots, out-of-scope routes, and ambiguous HTML fallback responses are excluded with a reason. Login discovery receives the scoped merged inventory separately from the GET-only probe candidates, so an independently observed POST login route can support configured authentication without becoming a JWT endpoint probe. JWT request counts include endpoint probes only, not Discovery or login requests.

For each selected `GET`, MicroScan records independent no-token and structurally valid JWT-with-invalid-signature cases. When `MICROSHIELD_USERNAME` and `MICROSHIELD_PASSWORD` are available from `.env` or the process environment, login discovery prioritizes observed POST authentication routes and then uses at most three bounded common POST candidates on the already-authorized target origin. Static login evidence can inform the request field names and form encoding. A successful login may yield a JWT or a session cookie; the value is kept in memory for that scan and never included in reports. Login requests are separate from JWT endpoint request counts. Missing credentials, failed login attempts, and unavailable login evidence are reported as skipped valid-token coverage without interrupting Discovery. Expired-token probing is not implemented and is recorded as `skipped`; MicroScan does not infer signing keys or mint expired tokens. A request error on one case does not prevent later cases or endpoints from running. Valid JSON, error envelopes, generic messages, and empty collections are not treated as resource disclosure. A potential resource finding requires a bounded sanitized sample of record-shaped data (field names and value types only; response values and raw bodies are not retained). If an error/denial signal and resource-record sample coexist, the report preserves the conflict and explains that the sample must be verified. Structured resource data without credentials is `potential` unless explicit endpoint metadata establishes the authentication policy: `authentication_required=true` can support a `confirmed` finding only when the same response does not indicate denial, while `false` identifies a public resource for that case. Without policy metadata, generic 2xx messages or bodies without resource records are `inconclusive`. HTTP 401/403 and body/challenge signals are evidence of denial, but do not by themselves prove that resource data was absent when the body could not be assessed. Endpoint selection is recalculated from the current Discovery result on each scan; selection or a mock test is not counted as an actual probe. The summary distinguishes discovered, selected, tested, partially tested, inconclusive, and untested endpoints from test-case outcomes and request attempts. Skipped and not-implemented counters are disjoint in the executive summary: not-implemented cases have raw `skipped` status but are excluded from the separate skipped count. Endpoint details and findings display the same sanitized test-case evidence.

The backend also produces a pentest conclusion and executive summary from the collected test-case evidence. Only `confirmed` and `potential` cases are emitted as vulnerability findings; `not_vulnerable_in_test` and coverage statuses remain test outcomes. Incomplete endpoint coverage, skipped/unimplemented cases, inconclusive results, and request errors prevent a clean negative conclusion. `No Vulnerabilities Detected in Tested Scope` is limited to a fully completed test scope and is not a claim that the system is secure. Discovery/scan failures return a `Scan Failed` report with no fabricated findings.

Passive BOLA correlation remains a separate analysis mode. It reuses only sanitized JSON evidence already captured by selected authenticated checks and sends no requests. Collection baselines retain observed identifiers, response fingerprints, and pagination/completeness limits. Matching IDs are reported as matched; an ID absent from an apparently complete captured collection is only a potential out-of-baseline observation, never confirmed BOLA by itself.

Opted-in loopback scans also run bounded active BOLA detail checks independently of the JWT endpoint-selection budget. After an authenticated collection response is captured, the scanner uses only identifiers present in actual response evidence and only detail-route templates discovered from the scan inventory. Identifiers absent from the observed authenticated collection baseline are prioritized. Requests use the existing authenticated token or cookie, are GET-only, remain on the configured loopback origin, and do not follow redirects. Set `MICROSCAN_BOLA_REQUEST_BUDGET` to an integer from 1 to 100 to adjust the independent per-scan request cap; the default is 10. The report records selection, send, response, sanitized path, status, content type, outcome, and baseline limitations. A successful JSON object response for an out-of-baseline identifier is a Potential finding only; active checks do not prove authorization policy or resource ownership. Missing authentication and unavailable or partial baselines are explicitly reported. Active BOLA request counts are separate from JWT request counts.

JWT evidence traversal defaults to three items per response array. Set `MICROSCAN_EVIDENCE_TRAVERSAL_LIMIT` to an integer from 1 to 25 to adjust this bounded limit; array entries beyond the configured value remain explicitly marked as unexamined, so the collection baseline stays partial. The sanitized resource-record sample count uses the same bound.

## File Discovery

File Discovery runs automatically as part of the existing `GET /scan?target=...` flow. Kiterunner, bounded common-path discovery, HTML link/form extraction, same-origin JavaScript analysis, endpoint correlation, and the existing security-testing stage contribute to one scan report. The frontend uses the `/scan?stream=true` form of the same API to display live stage updates; callers that omit `stream=true` continue to receive the original JSON response format plus discovery metadata.

The default wordlist is available from `GET /file-discovery/wordlists/default`; the standalone `POST /file-discovery` endpoint remains available for debugging. Requests use GET only, at most five requests per second and five concurrent connections, a 15-second timeout ceiling, and a 1 MiB response-body read limit. Results contain response metadata and short redacted evidence only; fetched bodies are not persisted.

For safety, File Discovery only accepts `localhost`, `127.0.0.1`, or `::1` on the existing lab ports 3000 and 8085, ignores environment proxy settings, and never follows redirects. JavaScript files are fetched only from the frontend's same origin. The scan target is the initial authorized origin. The trusted local-lab profile pairs the frontend and Gateway origins on ports 3000 and 8085, so a scan of `http://localhost:3000` can use `http://localhost:8085` without a manual Gateway environment setting. The Scan page's advanced scope field is only needed for other origins; those must be explicitly authorized. JavaScript references can identify candidate origins but cannot expand the authorized scope. `MICROSCAN_GATEWAY_TARGET` remains supported for compatibility.

Recursive Kiterunner discovery queues static GET `/api/*` paths observed in JavaScript or API-like HTML forms against explicitly scoped candidate origins. It deduplicates origin/path/method combinations, preserves non-GET methods and dynamic templates as evidence, and applies bounded recursion depth, target, seed-request, and per-command timeout limits. The scan history reports each round's target, seeds, exit code, new/duplicate results, and stop reason. A Gateway root is only origin evidence and is never treated as an API endpoint. Kiterunner and JavaScript discoveries remain discovery evidence, not proof that an endpoint is verified or vulnerable. Any endpoint considered by existing security tests remains subject to the module's existing explicit allowlist, target restrictions, and candidate-selection limits. HTML form methods and JavaScript POST/PUT/PATCH/DELETE hints are recorded but never sent by File Discovery or the seeded stage. Only clear File Discovery verification responses are marked verified; a 200 response matching a generic missing-path response remains not found. Discovery does not classify vulnerabilities.

Relative JavaScript paths are resolved against the explicitly authorized API origins only when the request path is supported by discovery evidence. Dynamic templates, POST and other non-GET methods, frontend routes, the Gateway root, and JavaScript origins outside the authorized scope are never literal seed requests. The original frontend URL, literal discovered path, method, and evidence are retained separately from `resolved_url`; POST and other non-GET methods are recorded without sending a verification request. Discovery history records each recursive round, its target, seed count, Kiterunner exit code, result totals, and stop reason; command failures include exit status and diagnostics. A 2xx HTML response is not treated as a verified API response. Discovery, verification, and security testing are separate: `security_status: tested` requires an actual executed security assessment, while unverified or unresolved records remain visible and are skipped for those tests. Security summaries distinguish eligible module input, selected endpoints, request attempts, and actually tested endpoints. The API Map consumes the unified discovery inventory and shows a local error message if map rendering fails.

Normalized `not_found` records (including seeded 404s and fingerprinted frontend HTML fallbacks) are excluded from the default endpoint list, API Map, and security-testing input, while their original status and source evidence remain available in the “Excluded / Not Found” audit view. A 404 that conflicts with direct or correlated route evidence remains visible as inconclusive; 401/403 and 405 observations are preserved in their blocked/inconclusive categories, including any `Allow` methods for 405 responses.

`MICROSCAN_GATEWAY_TARGET` is optional and is not needed for the paired localhost lab profile. File Discovery itself retains the existing local lab allowlist; it does not use arbitrary configured hosts as a reason to widen its HTTP request scope.

Run backend tests with `.\.venv\Scripts\python.exe -m unittest discover -s tests`. Pipeline and HTTP behavior tests use mocks. The Kiterunner CLI invocation was additionally exercised against a temporary loopback HTTP fixture; no live lab target was scanned. The existing `/scan` route and Kiterunner module remain compatible.

Login candidates require an observed `POST` route and authentication-flow evidence from discovery. A `GET` response with status 405 can corroborate a method only when its `Allow` header lists that method; it never creates or rewrites a POST discovery. Registration, logout, refresh, and session-check routes are not login candidates. Automatic credentials are sent only when frontend evidence establishes the request body fields and content type. MicroScan does not guess common login paths or payload schemas, and limits attempts to one request per eligible candidate. Credentials are loaded from the repository-root `.env` using `python-dotenv`; operating-system environment values take precedence. The root `.env` is ignored by Git; use `.env.example` as a template:

- `MICROSHIELD_USERNAME` and `MICROSHIELD_PASSWORD`: used only when discovered frontend request evidence identifies the matching credential fields and content type.
- `MICROSCAN_LOGIN_ENDPOINT`: optional path or same-origin absolute URL; automatic credential use still requires a matching discovered candidate and request contract.
- `MICROSCAN_LOGIN_PAYLOAD`: optional legacy JSON payload object, used instead of the username/password pair when present.
- `MICROSCAN_AUTH_CONFIG`: JSON object with a `payload` object, and optional `login_endpoint`, `content_type`, `method` (`POST` only), `token_field`, `auth_header`, and `auth_scheme`.
- `MICROSCAN_JWT_ENDPOINT_ALLOWLIST`: optional JSON array of explicit `{ "method": "GET", "path": "/api/resource/1" }` targets. Paths must be origin-relative and must not include query or fragment data. Only `GET` is probed; other configured methods are reported as skipped.
- `MICROSCAN_JWT_ENDPOINT_BUDGET`: optional Standard Scan automatic-selection cap (integer 1-100); defaults to five route groups. Full Scan does not apply this cap. It does not limit explicit allowlists.
- `MICROSCAN_PROTECTED_ENDPOINT`: legacy optional path, treated as one explicitly allowlisted `GET` target. It is not a substitute for an API-wide allowlist.

The payload must match the lab's real contract. MicroScan extracts a token only from supported response fields or the configured `token_field`; it recognizes a session cookie when no token is returned and sends a valid-token probe only after login actually succeeds. A successful HTTP status alone does not establish successful authentication. The authorization scheme is taken from configuration, the login response, or an observed challenge. If none is present but the returned token has the standard three-part JWT shape, MicroScan makes a best-effort `Bearer` request and labels that scheme as inferred rather than observed. Other token formats require an explicit or observed scheme. Passwords, tokens, cookies, and authorization headers are kept out of reports. `confirmed`, `potential`, `not_vulnerable_in_test`, `inconclusive`, and `skipped` describe only the evidence and coverage from this particular endpoint/test case.

Example allowlist:

```text
MICROSCAN_JWT_ENDPOINT_ALLOWLIST=[{"method":"GET","path":"/api/users/me"},{"method":"GET","path":"/api/orders/1"}]
```

Install backend dependencies from the repository root with `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`. Copy `.env.example` to `.env` and replace the placeholders with authorized lab credentials (or set the environment variables in your shell). Do not commit `.env` or put credentials in reports:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# Edit .env with the authorized lab values before starting the backend.
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

To run basic unauthenticated checks, leave the authentication variables unset. Start the frontend in a separate shell with `cd frontend` and `npm run dev`, then enter the authorized target origin on the Scan page. Unit tests use mocked HTTP responses; they do not establish the behavior or vulnerability status of a live lab.
